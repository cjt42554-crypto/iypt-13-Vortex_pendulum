# PR-2A 页面回复与仓库机器门差异统一裁决

审查基线为：

## 1. 总裁决

### 1.1 唯一首次正式观测通过码

自本裁决起，首次正式 HW2R 的唯一合法通过码为：

`PASS-PR2A-HW2R-FORMAL-OBSERVATION-READY`

以下旧码不再具有解锁效力：

`PASS-HW2R-PRE-OBSERVATION-READINESS`

旧码可以保留在历史文档中，但机器门、current、manifest、sidecar、入口输出和后续证据不得再把它写成活动通过码。

### 1.2 机器门版本

新增活动机器门：

`VP-HW2R-PRE-OBSERVATION-READINESS-v2`

v1 保持历史字节不变。v2 取代 v1 作为正式入口读取的唯一活动门。当前 v2 状态为：

- `status=NOT_READY`；
- `formalObservationAuthorized=false`；
- `attainedPassCode=null`；
- 七项活动 P0 全部 `OPEN`；
- 结果承载科学运行继续禁止。

### 1.3 当前不得启动的任务

在 v2 机器门真实达到唯一通过码前，禁止启动：

- 正式 HW2R；
- 任何以正式 HW2R 名义进行的 calibration、warmup 或 repeat；
- H2-X、H2-N 正式矩阵；
- H3；
- `HW1-primary`；
- `HW1-repeat`；
- 任何完整八 case 结果承载运行；
- 科学 payload 读取。

## 2. 分层原则

首次正式 HW2R 之前只要求闭合会直接影响下列事项的缺口：

1. 候选间可比性和候选集合真实性；
2. 首次观测本身的主机安全、进程收容和失败证据；
3. 结果盲时间顺序；
4. GPU/CPU/hybrid 生命周期是否代表将来运行；
5. 观测实现、合同、CI 和主机现场是否已封存。

以下内容不必在首次 HW2R 前执行，只要合同、门值和触发器已经结果前冻结：

- H2-X 全部精确等价资格；
- H2-N 条件完整资格；
- H3P 最终故障矩阵和两个真实环境封存。

这些任务必须在 HW2R 后、PR-2B 前完成，且不得结果后修改已冻结门值。

## 3. 首次正式 HW2R 前的完整七项 P0

以下七项是唯一权威的活动 P0 清单。PR-2A v1 中的旧七项映射到本清单；页面回复中的额外事项按本节与第 4 节分层。

### P0-1：可比 A8R 操作图与 superseding protocol

机器 ID：

`P0-COMPARABLE-A8R-OPERATION-GRAPH-AND-PROTOCOL`

必须同时满足：

- 新建并冻结取代当前 v2 测量语义的 superseding protocol，推荐版本 ID 为 v3；
- 版本号不是目的，必要条件是旧 v2 不得结果后原地改写；
- 最终选择使用的代表负载必须执行冻结 A8R 的实际缩短操作图，包括 Float64 D2Q9、MRT、Guo forcing、Brinkman、开放边界、分析期 pre/post 人口路径、独立 raw 力身份、A2 重算、场诊断、trace、shard 和 aggregation；
- R1 可继续作为微内核与设备生命周期诊断，但不得独自决定最终后端；
- R2 或等价端到端负载必须由冻结八 case 定义程序化生成；
- 所有参与同一次排序的候选必须使用同一工作量身份和同一端到端计分模型；
- 禁止跨 R1/R2 或不同工作单位直接计算 speedup。

因此，页面回复中的“HW2R v3/真实 R1”属于首次观测前 P0，但准确要求是“superseding protocol 加真实可比端到端操作图”，而不是机械要求某个文件必须命名为 v3。

### P0-2：distinct executor、去重与有效资源数

机器 ID：

`P0-DISTINCT-EXECUTORS-AND-EFFECTIVE-RESOURCES`

必须同时满足：

- persistent worker、fresh case process、shard/data-layout 路线使用实质不同的 executor；
- 每个候选绑定不可变 executor fingerprint；
- fingerprint 相同的候选在进入候选集合前去重；
- `workloadId` 与实际执行路径一致；
- `declaredResourceCount`、`effectiveResourceCount` 和 `activeWorkerCount` 分开记录；
- 利用率、扩展效率和内存模型只能使用实际有效资源数；
- 八 case 只能激活八个 case worker，超出部分不得伪装成额外并行资源；
- Node worker 与 case process 若没有实质生命周期差异，只保留一个候选。

### P0-3：运行期持久 GPU 与代表性 hybrid

机器 ID：

`P0-RUN-LIFETIME-PERSISTENT-GPU-AND-HYBRID`

必须同时满足：

- 一个 formal repeat 内，GPU context、program、queue 和 reusable buffer 跨 D24、D36、D54 case 持久；
- 按尺寸缓存或安全重分配 buffer，且生命周期进入机器证据；
- cold initialization、size transition、steady compute、H2D、D2H、synchronization、audit 和 cleanup 分项计时；
- GPU/hybrid 候选启动前分别检查外来 GPU 计算进程；
- hybrid 按冻结成本模型进行结果盲分工；
- combined hybrid 验证 case 唯一归属、无缺失、无重复、失败时无 silent fallback；
- CPU/GPU 侧身份、聚合顺序和清理状态可审计。

因此，GPU context 跨不同尺寸 case 持久化是首次观测前 P0，而不是 HW2R 后再补的解释性优化。

### P0-4：数值身份时间顺序与 unresolved fail-closed

机器 ID：

`P0-NUMERICAL-IDENTITY-ORDER-AND-UNRESOLVED-SELECTION`

必须同时满足：

- HW2R 只记录 surrogate correctness、时间、资源和候选状态；
- 在 H2-X/H2-N 实际通过前不得写 `numericalIdentityPass=true`；
- exact 路线写 `NUMERICAL_IDENTITY_PENDING_H2X`；
- non-exact 路线写 `NUMERICAL_IDENTITY_PENDING_H2N`；
- finalizer 只接受经过哈希验证的 H2-X 或完整 H2-N 证据；
- measurement-invalid、deferred、unavailable、execution-failed、unknown-state 和 identity-pending 候选，只要可能净快 10% 以上，就阻断最终选择；
- 95% near-best 集合只在工作量可比、测量有效、安全且数值身份已接受的候选中计算。

### P0-5：双向校准与全阶段硬安全监督

机器 ID：

`P0-BIDIRECTIONAL-CALIBRATION-AND-FULL-PHASE-SAFETY`

必须同时满足：

- calibration 可以按冻结规则放大过短工作量，也可以从首次过长观测确定性缩小或预测下一批次；
- 正式 repeat 开始后工作量冻结；
- calibration、warmup 和 formal repeat 均运行在同一有限 cgroup 与同一安全边界内；
- 三阶段均监督系统内存保留、cgroup current/peak/high、swap、OOM、热和外来 GPU 进程；
- 任何硬安全门越界立即停止当前候选并阻断本次正式 attempt；
- 安全监督证据必须保留阶段、时间、资源基线、触发字段和停止结果。

这里区分两层：

- 上述硬安全监督属于首次观测前 P0；
- 更丰富的 phase-resolved 利用率解释、性能归因和最终 soak 统计可以在 HW2R 后、PR-2B 前完善。

### P0-6：子进程收容、超时和失败证据

机器 ID：

`P0-CHILD-CONTAINMENT-TIMEOUT-AND-FAILURE-EVIDENCE`

必须同时满足：

- 所有 Node/native/GPU child 有冻结的 wall-clock timeout；
- child 位于本任务专用进程组或等价可整体收容范围；
- timeout 或异常时先停止新派发，再只终止本任务子进程；
- 清理后核验无残留 PID、无残留 cgroup task、无临时 native/GPU service；
- 不得使用宽泛 `pkill`、`killall` 或操作无关进程；
- 失败证据至少包含 candidate、stage、failure code、sanitized message SHA-256、exit code/signal、timeout、资源前后快照、cleanup 和 residual-process 字段；
- one-worker 实测或保守静态下界控制 wider launch，cgroup peak 加 headroom 低于上限。

因此，页面回复中的 timeout/PGID/残留核验属于首次观测前 P0。

### P0-7：观测前封存、入口强制和唯一通过码

机器 ID：

`P0-PREOBSERVATION-SEAL-ENTRYPOINT-AND-UNIQUE-PASS-CODE`

必须同时满足：

- 正式 runner 自身调用活动机器门，不能仅依赖人工先运行 audit 命令；
- 正式 finalizer 同样不得绕过活动机器门；
- 七项 P0 均 `CLOSED`，每项有 committed/pushed closure evidence；
- 生成 pre-observation manifest 和 sidecar；
- manifest 绑定 decision、gate、protocol、implementation commit/tree、candidate matrix、tests、CI run、host preflight 和禁止科学运行声明；
- sidecar 同时绑定 stored SHA-256 与 canonical SHA-256；
- `main` 干净且 `HEAD == origin/main`；
- H1/H2/H3/_shared 轻量测试通过；
- Markdown 与 Simulation 两个 GitHub workflow 通过；
- 没有活动结果承载运行，没有科学 payload 读取；
- gate 的 `attainedPassCode` 必须精确等于：

`PASS-PR2A-HW2R-FORMAL-OBSERVATION-READY`

pre-observation manifest/sidecar 因此属于首次观测前 P0 封存门。

## 4. HW2R 后、PR-2B 前必须完成的要求

以下要求不再阻断首次正式 HW2R，但必须在 PR-2B 前全部闭合。

### 4.1 H2-X 全资格

包括：

- 冻结 worker 数完整矩阵；
- 实际 completion、delivery、receipt、discovery 和 aggregation order 扰动；
- 三个独立环境；
- population、force identity 和 shortened payload 哈希；
- missing、duplicate、corrupt、partial、source drift、contract drift、worker exit/signal、cross-run、cross-environment、runtime fallback 等全负例；
- D54 内存和主机安全证据。

因此，PR-2A v1 中 `P0-H2X-ORDER-AND-SHARD-BINDING` 的剩余“全负例和实际完成顺序”从首次观测前门移到 HW2R 后、PR-2B 前。观测前只要求 HW2R 自身的 shard/identity 不产生不可比或不可审计数据。

### 4.2 H2-N 条件完整资格

首次观测前必须已经冻结 H2-N 合同、阈值、evidence envelope、10% 触发器和 fail-closed validator。

HW2R 后执行：

1. stage-0；
2. 与已通过 H2-X 的端到端路线比较；
3. 若净收益不超过 10%，记录 `DEFERRED-H2N-NO-MATERIAL-END-TO-END-GAIN`；
4. 若净收益严格超过 10%，实现并执行 full evaluator、negative dispatcher 和完整数值资格；
5. 工具链或资源延期且仍可能快 10% 以上时，阻止最终选择。

因此，H2-N full evaluator/negative dispatcher 的执行与条件实现属于 HW2R 后、PR-2B 前；其合同和接受语义必须在首次观测前冻结。

### 4.3 H3P 全故障矩阵和真实双环境 seal

HW2R 选出候选且 H2-X/H2-N 结论闭合后，才有足够信息建立最终 H3 环境。PR-2B 前必须完成：

- H3P 全故障矩阵；
- atomic shard、sidecar 和 recovery；
- primary/repeat cross-reuse 拒绝；
- source、implementation、dependency、device 和 filesystem identity；
- 两个真实独立环境创建和 seal，但不得启动 H3；
- 环境之间无共享 shard、cache、temp 或 inode。

因此，H3P 全故障矩阵与双环境 seal 属于 HW2R 后、PR-2B 前。

### 4.4 观测后资源和性能终局

HW2R 后还必须形成：

- phase-resolved CPU/GPU 利用率解释；
- CPU 扩展或饱和曲线；
- GPU busy、transfer、synchronization 和热证据；
- 端到端加速至少 1.50；
- 达到全部可比合格候选最佳吞吐的至少 95%；
- 没有潜在大于 10% 的 unresolved 候选；
- 最终 hardware selection evidence 与 sidecar。
