`ACCEPT-A8R-V2P1-PRO-P1-RESULT-BLIND-REPAIR`

6. 当前仍不存在 A8R 数值 PASS、INCONCLUSIVE 或 NO-GO。

## 3. P1 接受理由

### 3.1 sidecar 格式已经闭合

运行器、A8Q 锚核验和研究产物断言器现在共享
`expectedArtifactSidecarText()`。该函数显式生成两个真实的 `"\n"`，
消除了上一版 JavaScript 行续接造成的合法 sidecar 必然失败。

### 3.2 repeat 门已经改为 fail-closed

P1 现在要求：

- primary 和 repeat 参数同时存在；
- 规范化绝对路径不同；
- `realpath` 后的路径不同；
- 两个 sidecar 路径及 `realpath` 不同；
- 两份 gzip 逐字节一致；
- 两份 sidecar 逐字节一致；
- 每一份 gzip 都能与自己的两行 sidecar 闭合。

缺 repeat、同一规范化路径、错误 sidecar 和合法双文件均有 CLI
端到端测试。机器门同时明确承认：不同路径和字节一致不能单独证明第二次
计算确实独立执行，研究报告仍须记录第二次运行从干净环境和第一个算例开始。

### 3.3 正式求解器执行默认硬锁

P1 身份把执行状态设为
`LOCKED_PENDING_POST_P1_PRO_REVIEW`，授权范围为空。
研究包入口和 `runBrinkmanMultiresolutionV2P1Case()` 都会在第一个
`D2Q9MrtBrinkmanSolver` 构造前抛错。单算例适配器中的抛错位于
普通失败结果转换之外，因此不会把未授权执行伪装成八条普通失败轨迹。

### 3.4 运行时来源身份已经覆盖主要传递依赖

前置门从三个结果相关入口出发，使用 TypeScript 语法树递归收集仓库内
静态导入，并额外绑定：

- `package.json`；
- `package-lock.json`；
- `tsconfig.json`；
- 精确 LFS 规则；
- 合同测试、支持测试、工件测试、汇总测试和 P1 测试。

该闭包包含 `benchmark-metrics.ts`、`benchmark-contract.ts`、正式
`lbm.ts`、A8Q 复用实现和流式 JSON 依赖。工作树中的每个闭包文件必须与
明确 P1 提交中的字节一致。它不再要求所有旧科学文件都被人为重新修改到同一
提交。

### 3.5 科学算法没有发生结果后改写

P1 没有改动周期选择、六周期积分、Minkowski 三值趋势、D54 四指标屏蔽、
D24 公共投影、控制体人口动量恒等式或 A2 公式重算。改动集中在授权、
来源身份、repeat 闭合、sidecar 和测试基础设施。

## 4. 非阻塞剩余限制

### 4.1 `realpath` 不排除硬链接别名

两个不同路径可以是同一 inode 的硬链接；`realpath` 不能识别这一情形。
这不阻塞本轮烟雾解锁，因为烟雾阶段不生成或断言研究 repeat 产物。但在研究
矩阵获得授权前，repeat helper 应在平台提供稳定 inode 时拒绝 gzip 或
sidecar 的相同 `(dev, ino)`；无论是否增加该机器门，资格报告仍必须保留
干净环境独立复跑记录。

### 4.2 锁文件不等于已安装依赖身份

`package-lock.json` 已进入提交树，但运行中的 `node_modules` 仍由执行环境
决定。因此烟雾实现提交后必须重新执行干净 `npm ci`，并在烟雾证据中记录
Node、V8、zlib、平台和架构。该限制不要求生产级供应链证明。

### 4.3 GitHub Actions 红灯不是 P1 新增错误

P1 提交的仓库级 Markdown 检查仍失败，但日志只报告 A8O 和 A8P 两份冻结
旧裁决中的四个既有命中。P1 修改文件没有新增数学格式命中。该 CI 不能证明
P1 的 TypeScript 测试通过，因为当前工作流只执行 Markdown 检查。

## 5. 下一阶段唯一允许的两个正式烟雾

两个烟雾均使用 v2.1 冻结的 `D=24`、mask 半厚度 `0.75`、基线相位、
`penalizationTimeSteps=1`、入口格子速度 `0.05` 和新鲜均匀初态。

### 5.1 固定圆柱烟雾

- `body="fixed-cylinder"`；
- 恰好 40 个 accepted steps；
- 不使用 checkpoint 恢复；
- 每步保存并核验步前、步后人口副本；
- 独立解析 mask 必须与正式 mask 逐元素相等；
- 非零 mask 和重建 Brinkman 力支撑必须位于冻结控制体内；
- 每步原始人口动量恒等式和 A2 公式重算分别通过各自舍入界；
- 每步正式修正载荷必须等于正式原始反力加正式虚拟内部流体修正；
- 全部记录必须有限。

### 5.2 `body=null` 烟雾

- `body=null`；
- 恰好 40 个 accepted steps；
- 控制体中心仍使用对应冻结定义的 `bodyCenterX/bodyCenterY`；
- 不允许移动或删除控制体；
- 独立 mask 全零，非零 mask 和非零 Brinkman 力计数均为零；
- 正式原始 Brinkman 反力和正式 A2 修正应为精确零；
- 独立控制体原始反力与正式零值的残差仍按冻结绝对舍入界判定；
- 每步 A2 公式重算和修正载荷分别闭合；
- 全部记录必须有限。

任何一个烟雾失败都只表示实现或集成证据未闭合，不能产生 Brinkman 物理路线
NO-GO，也不能改变 A8Q 或 A8R 的科学门。

## 6. 烟雾授权必须与研究授权隔离

下一提交不得把现有无参数授权函数简单改成“允许执行”。否则
`runBrinkmanMultiresolutionV2P1Case()` 会沿冻结定义运行完整研究时长，
等价于间接解锁研究矩阵。

必须采用显式作用域，至少区分：

- `FORMAL_FORCED_FIXED_CYLINDER_SMOKE_40`；
- `FORMAL_UNFORCED_BODY_NULL_SMOKE_40`；
- `RESEARCH_MATRIX`。

本裁决只允许前两个作用域。现有完整单算例函数和
`brinkman-multiresolution-v2-1` 研究入口必须以 `RESEARCH_MATRIX`
作用域继续抛错。烟雾应使用独立的恰好 40 步适配器，不得调用完整研究函数后
提前截断。

## 7. 结果前提交顺序

Codex 下一轮必须按以下顺序工作：

1. 建立烟雾授权和无结果烟雾实现提交，绑定本审查文件及其提交；
2. 在该提交中加入烟雾作用域测试、40 步上界测试、研究作用域拒绝测试、
   输出路径隔离测试和必要的 hard-link 负向测试；
3. 运行 `npm ci`、候选包测试、TypeScript 和 Node 语法检查；
4. 将无结果烟雾实现提交推送到远程 `main`；
5. 确认 `HEAD == origin/main`、工作树干净、前置门和来源树通过；
6. 才能执行两个正式 40 步烟雾；
7. 将烟雾机器证据和报告作为独立结果后提交推送；
8. 停止并再次交回独立 Pro。

不得在烟雾结果揭示后修改门值、作用域、步数、几何、控制体或力身份公式。

## 10. 当前结论上限

P1 结果盲修订可以接受，并且只足以进入正式求解器集成烟雾阶段。

即使两个烟雾全部通过，也只说明：

- 候选人口适配器能够与正式求解器执行 40 步；
- 控制体原始人口恒等式和 A2 重算在两个短程案例中机器闭合；
- 授权、来源和输出隔离按预注册规则工作。

它不建立长期稳定性、周期成熟性、三分辨率趋势、mask/相位稳健性、
Brinkman 锐界面、无滑移极限、连续应力载荷、正式程序接入、装置预测或实验
验证。
