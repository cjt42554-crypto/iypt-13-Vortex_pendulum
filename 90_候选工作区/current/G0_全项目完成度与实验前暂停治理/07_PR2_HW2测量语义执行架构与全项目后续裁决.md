## 3. 当前候选选择是否有效

### 3.1 有效部分

当前选择在非常窄的意义下是机械有效的：

- 评估器按已提交代码执行；
- 门值没有结果后改动；
- 只在 `PROBE_PASS` 子集内排序；
- 三个通过候选中 2 线程 OpenMP 的吞吐最高；
- 证据完整保留了未通过候选，而不是选择性删除；
- 选择结果可以从机器证据重算。

因此不得把证据描述为伪造、缺失或未按代码执行。

### 3.2 无效部分

当前选择作为 H3 后端选择无效，原因不是单一门值过严，而是协议、测量和选择集合形成了结构性偏差。

#### 3.2.1 固定工作量与 15 秒下限互相冲突

v1 先把串行家族校准到约 55 秒，再给同家族全部候选相同工作量。于是任何加速比大于：

`55 / 15 = 3.67`

的候选都必然低于 15 秒下限。

因此，计时窗不是在淘汰慢或不稳定候选，而是在系统性淘汰高加速候选。16 核 OpenMP、Node w08、GPU 和 hybrid 均受到这一机制影响。

15–60 秒门本身合理；错误在于没有按候选放大批次数，使每个候选的有效计时窗都进入该范围。

#### 3.2.2 “95% 最优”只在通过子集计算

评估器先删除全部 `PROBE_NO_GO`，再在三个 `PROBE_PASS` 中计算最佳吞吐和 95% 门。

只要高吞吐候选因测量无效而被标为 `PROBE_NO_GO`，低吞吐候选就会自动成为“100% 最优”。这不满足父合同“在全部安全、正确、可测候选中接近最优”的目标。

正确语义必须区分：

1. `MEASUREMENT_INVALID`；
2. `SAFETY_NO_GO`；
3. `CORRECTNESS_NO_GO`；
4. `UTILIZATION_NO_GO`；
5. `QUALIFIED`.

只要存在测量无效且原始数据表明可能快 10% 以上的候选，就不得形成最终选择。

#### 3.2.3 GPU 遥测采样不足

GPU 完整重复约 0.354 秒，资源采样间隔为 250 ms。基线和结束快照之外，最多只有极少中间点。以这些样本的中位数推断 GPU busy、热状态或持续利用率不可靠。

`gpuBusyFraction=0` 在这里更可能表示采样没有命中计算窗，而不是 GPU 没有执行。它可以使本次测量无效，但不能证明 GPU 路线本身 NO-GO。

GPU 代表性测量至少必须满足以下一项：

- 计算窗内不少于 30 个有效 GPU 遥测样本；
- 使用 CUDA event、CUPTI、NVML 高频接口或等价设备侧计时；
- 候选批次被放大到足够长，250 ms 轮询可解析持续状态。

#### 3.2.4 GPU CPU-feed 判定是循环定义

当前实现把：

`gpuBusyFraction < 0.60`

直接转换为：

`cpuFeedSingleThreadBottleneck=true`

随后又以该布尔值触发 `GPU_CPU_FEED_GATE`。

低 GPU busy 可能来自短任务、采样漏失、上下文建立、JIT、传输、同步、工作量过小或 CPU 喂数。它不能单独证明 CPU 喂数瓶颈。

未来必须独立测量：

- CPU 准备时间；
- H2D/D2H；
- kernel 时间；
- 同步时间；
- 排队空洞；
- 单线程提交占比；
- 持续 GPU 空闲区间。

#### 3.2.5 “端到端”边界不一致

协议声明包括 build、startup、IPC、transfer、audit 和 aggregation。

实际实现先构建 native 二进制，再进入正式计时，因此 build 没有计入候选墙钟。GPU 每次执行却重新创建 context、JIT module、分配显存、运行、回传和销毁 context；这些开销全部计入。

这形成不对称：

- CPU 编译是批次外一次性开销；
- GPU JIT/context 是每次重复开销；
- H3 实际架构很可能是每个 worker 或设备一次初始化，而不是每个小任务重建；
- shard、A8R 力身份审计和规范写入均未被代表性计入。

未来必须分别报告：

1. build/toolchain provisioning；
2. cold process/device initialization；
3. steady-state compute；
4. transfer/IPC；
5. audit；
6. shard write/verify；
7. final aggregation；
8. H3 端到端模型。

最终选择使用 H3 端到端模型，不能混合不同生命周期边界。

#### 3.2.6 合成工作负载不代表 A8R

v1 工作负载是独立 `u32` 元素上的精确模 $2^{32}$ 迭代，最后只写一次数组并计算摘要。它证明并行分片、设备调用和摘要一致性，但不代表：

- Float64 D2Q9 MRT 碰撞；
- scatter streaming；
- Zou–He 开放边界；
- Brinkman mask 和力；
- 每步宏观量；
- 分析窗内 pre/post 全人口副本；
- 独立力身份复算；
- 场诊断；
- 大型对象 trace；
- case shard 和最终规范聚合。

因此当前吞吐不能作为 A8R 运行速度的估计，也不能决定科学后端。

#### 3.2.7 跨家族基线不完全同构

JS 和 native 家族使用不同元素数、轮数和基线摘要。MLUPS 按元素乘轮数归一，但 JS worker、native OpenMP、CUDA、进程启动和摘要路径的单位工作成本不一定相同。

未来可以保留微基准用于设备发现，但最终选择必须基于同一代表性 A8R 操作图或可证明等价的工作单位。

#### 3.2.8 内存带宽指标不能用于当前工作负载解释

当前 `memoryBandwidthFraction` 以 `elements * 4 / wallTime` 估算，而工作负载在寄存器中执行大量 rounds 后只写最终值。该指标没有把 rounds 对计算强度的作用与实际内存流量分开，也与真实 LBM 每步多数组读写不相似。

此外，`additionalCpuGainAtBandwidthSaturation` 被固定写为 1，而不是由相邻资源点实测得到。当前 CPU 带宽饱和与并行效率分流没有证据效力。

## 4. WP-HW2 的精确定性

WP-HW2 是父工作包，不应因一个子尝试的语义缺陷直接整体 NO-GO，也不能因候选专用 PASS 升级为 PASS。

当前状态：

`WP-HW2 = IN_PROGRESS`

其已终止子状态：

`HW2-V1 = INCONCLUSIVE-HW2-V1-CANDIDATE-SELECTION-MEASUREMENT-SEMANTICS`

新增活动子工作包：

- `WP-HW2R`：代表性测量协议和完整重资格；
- `WP-H2X`：精确执行等价；
- `WP-H2N`：非逐字节后端的条件数值资格；
- `WP-H3P`：H3 产物、shard、恢复和两个环境的结果前准备。

WP-HW2 只有在下列任一出口成立时终止：

### PASS 出口

- `PASS-HW2-FINAL-HARDWARE-SELECTION-CANDIDATE-ONLY`
- 并且选中后端已通过 H2-X，或已通过完整 H2-N；
- 并且没有未处置的可访问候选仍有超过 10% 代表性净提速可能。

### NO-GO 出口

`NO-GO-A8R-HW1-HARDWARE-QUALIFICATION`

该出口要求所有可访问候选均有结果前协议下的有效失败证据，不能由 v1 测量无效直接触发。

### DEFERRED 出口

`DEFERRED-HW2-UNSAFE-RESOURCE-WINDOW`

只适用于外来进程、内存、安全或设备访问当前确实不允许探针的情形；必须记录重新触发条件。

## 5. “充分利用硬件”的活动定义

“充分利用”不等于 CPU 和 GPU 必须同时 100%，也不等于选择原始微基准峰值最高者。

活动定义为：

1. 所有可访问、可能提供超过 10% 端到端净收益的资源类别均已代表性评估；
2. 没有候选因计时过短、采样漏失或生命周期边界不一致而被误判为实质 NO-GO；
3. 被选配置在正确性、安全和数值身份成立的前提下，端到端吞吐不低于全部合格候选最佳值的 95%；
4. CPU 路线给出资源扩展曲线和饱和依据；
5. GPU 路线给出持续设备利用、传输、同步、初始化和审计开销；
6. 若继续增加 CPU/GPU 只带来不超过 5% 净收益，允许低于满载；
7. 若 GPU 或宽 CPU 路线仍可能快 10% 以上，则不能以实现复杂为由直接跳过；
8. 结论只对绑定主机、驱动、编译器、资源窗口和科学身份有效。

当前 2 线程 OpenMP 不满足这一活动定义。

## 6. HW2R v2 代表性测量协议

### 6.1 结果前冻结顺序

必须依次形成并推送：

1. `VP-HW2-REPRESENTATIVE-QUALIFICATION-PROTOCOL-v2`；
2. v2 schema；
3. v2 合同测试；
4. v2 测量器、遥测器和选择器；
5. 代表性工作负载实现；
6. 首次 v2 性能运行授权；
7. 完整 v2 机器证据和 sidecar。

v1 合同、实现、证据和报告保持逐字节不变。

### 6.2 候选特定计时

每个候选独立放大正式批次，使每次有效稳态测量落在 20–45 秒，硬容许范围仍为 15–60 秒。

禁止把“低于 15 秒”记为候选性能 NO-GO。正确分类是：

`MEASUREMENT_INVALID-WORKLOAD-TOO-SHORT`

随后必须在同一冻结协议内自动、结果盲地放大批次并重新测量。

为避免结果后挑选，放大算法必须在首次 v2 性能观察前冻结，例如：

- 最多三次短校准；
- 以中位吞吐预测批次数；
- 批次数只能按确定性规则增加；
- 正式三次重复的工作量固定；
- 正式重复开始后不再调整。

### 6.3 生命周期分解

每个候选必须分别记录：

- build/provision；
- cold process/device initialization；
- warmup；
- steady-state compute；
- IPC/transfer；
- audit；
- shard serialization、fsync 和 hash；
- final aggregation；
- cleanup。

H3 端到端估计为：

`一次性初始化 + 八 case 调度与计算 + 八 shard 验证 + 最终聚合`

不能用每个微任务都重建 context 的路径代表持久 GPU worker，也不能把 build 全部排除而声称完全端到端。

### 6.4 CPU 候选矩阵

至少测量：

- 1、2、4、8、12、16 个物理核；
- 24、32 逻辑线程仅作为 SMT 扩展，资源安全时测量；
- 单进程 OpenMP/native；
- 多进程 case 级调度；
- Node worker/process；
- 物理核 pinning；
- 两个 L3/CCD 的分组和跨组布置；
- case 成本感知调度。

每个相邻资源点必须记录吞吐增益。只有实际增益不超过 5%，或可持续内存带宽达到冻结饱和门，才可声称不需要更多 CPU。

### 6.5 GPU 与混合候选矩阵

GPU 路线至少包括：

- persistent CUDA context；
- module/JIT 缓存；
- persistent device buffers；
- 多次 kernel 批处理；
- 独立 CUDA event 时间；
- 不少于 30 个有效 GPU 遥测样本或等价高频计数；
- H2D、D2H、同步、审计分别计时；
- 真实 A8R 数据布局的代表性传输；
- CPU 2、4、8 线程与 GPU 的至少三种负载分割；
- 自动分割必须基于结果前冻结的性能模型，禁止读取科学值。

GPU 不得仅凭 v1 的 `gpuBusy=0` 或 42.6% transfer 结论被淘汰。

### 6.6 完整候选集合和选择语义

v2 必须完整重跑全部候选类别，不能只重试 v1 中快速或失败的候选。

选择顺序固定为：

1. 静态可访问；
2. 测量有效；
3. 正确性通过；
4. 安全通过；
5. 数值身份通过；
6. 利用率/效率通过或有饱和证明；
7. 性能门通过；
8. 在全部合格候选中计算最佳吞吐；
9. 选择达到最佳值 95% 以上的候选；
10. 若多个候选进入 95%，按更低科学语义风险、更低内存、较低治理复杂度和确定性顺序决胜。

只要存在 `MEASUREMENT_INVALID` 且可能提供超过 10% 净收益的候选，选择器必须 fail-closed。

## 7. 代表性工作负载

v2 保留 u32 微基准作为设备发现和执行框架 smoke，但不得再作为最终选择依据。

最终选择工作负载必须包括：

### R0：执行框架 smoke

- 固定无科学字节；
- 验证 worker、IPC、GPU 调用、摘要和证据封装；
- 不参与最终硬件选择。

### R1：A8R 操作图代表负载

- D54 尺寸；
- 正式 Float64 D2Q9 数据布局；
- MRT、Guo forcing、Brinkman、streaming 和开放边界；
- 完整分析步 pre/post 人口路径；
- 完整力身份和 A2 复算；
- 场诊断；
- 紧凑 trace/shard/hash；
- 不输出科学数值，只输出哈希、相等布尔值、时间和资源字段。

### R2：case 调度代表负载

- 使用冻结八 case 的成本结构；
- 可以缩短每个 case 的步数，但必须保留 D24/D36/D54 比例和完整代码路径；
- 比较 1、2、3、4 及内存安全上限 worker；
- 验证完成顺序不改变规范字节；
- 记录调度空洞、负载不均和峰值内存。

只有 R1/R2 可以决定 H3 执行架构。

## 8. H2-X 精确执行等价路线

### 8.1 首选低语义风险路线

现有 A8R 源已导出单 case 运行函数和资格聚合函数。下一阶段首选在新候选路径建立：

- process/worker pool；
- case scheduler；
- atomic case shard；
- deterministic aggregator；
- result-blind oracle；
- H3 runner。

首选路线只改变执行调度、case 隔离和产物封装，不改变现有 case 内浮点运算顺序。

该路线不需要修改：

- 既有 A8R v2.1 科学源；
- 正式 `lbm.ts`；
- A8R 合同或科学门。

### 8.2 H2-X 必过门

H2-X 必须在结果前合同下同时通过：

1. 八 case 定义和全部冻结源哈希相同；
2. 新鲜初态相同；
3. 指定 checkpoint 的完整人口原始字节相同；
4. 分析第一步和冻结审计步的 pre/post 人口字节相同；
5. 每步力身份摘要哈希相同；
6. 缩短但完整 case 的 scientific payload 规范哈希相同；
7. 1 worker 与选中 worker 数相同；
8. 完成顺序扰动后聚合相同；
9. missing、duplicate、corrupt、source drift、worker failure 全部 fail-closed；
10. execution 字段不能进入 scientific payload；
11. 三个独立轻量环境一致；
12. D54 代表负载通过内存、安全和性能门；
13. 不显示或持久化哈希前科学值。

通过码：

`PASS-H2X-EXACT-SCIENTIFIC-EXECUTION-EQUIVALENCE-CANDIDATE-ONLY`

### 8.3 case shard 与恢复

每个 shard 只有在一个 case 从 step 0 完整结束、来源和内部结构门通过后才能原子写入。

H3 结果前合同必须允许：

- 同一 `HW1-primary` 或同一 `HW1-repeat` 身份在主机异常后继续使用已经完整、哈希闭合的本运行 shard；
- 被中断 case 必须从 step 0 重跑；
- 不允许 primary/repeat 互用 shard；
- 不允许跨实现提交复用；
- 不允许依据 shard 科学值调整后续调度；
- `.partial-*` 只能删除或隔离，不能升级为完成 shard。

这一规则避免再次因主机关机丢失全部已完成 case，同时不削弱独立复跑。

## 9. H2-N 非逐字节后端

### 9.1 触发条件

以下任一条件触发 H2-N：

- native/OpenMP 实际 case 内并行改变浮点或归约顺序；
- GPU 改变内核、精度、归约、边界或数据布局；
- SIMD/native 无法通过 H2-X；
- H2-X 后端不是代表性最优，且 H2-N 候选预计净收益超过 10%。

### 9.2 阶段 0：代表性可行性

必须先冻结 H2-N stage-0 合同，覆盖：

- D2Q9 equilibrium 和 moments；
- MRT collision；
- Guo forcing；
- Brinkman mask/force；
- streaming；
- 开放边界；
- `body=null`；
- 固定体；
- 人口、质量、动量和力交换；
- 指定 checkpoint 场量；
- 小/中/D54 代表尺寸；
- cold/steady-state 性能。

stage-0 最高输出：

- `PASS-H2N-STAGE0-REPRESENTATIVE-FEASIBILITY`;
- `NO-GO-H2N-STAGE0-NUMERIC-OR-PERFORMANCE`;
- `DEFERRED-H2N-TOOLCHAIN-OR-RESOURCE`.

若 stage-0 端到端净收益不超过选中 H2-X 的 10%，可以有效停止 H2-N：

`DEFERRED-H2N-NO-MATERIAL-END-TO-END-GAIN`

### 9.3 完整数值资格

若 stage-0 显示超过 10% 的代表性净收益，必须完成：

- 质量和动量账；
- 每步 Brinkman 交换；
- raw 和 A2 力；
- 边界负例；
- 稳定性；
- 网格/时间/精度；
- reduction 误差；
- 跨设备确定性；
- 统计指标容差；
- 两个独立实现或一个实现加独立参考；
- 完整来源和编译器/驱动身份。

H2-N 必须使用新算法/后端身份，不能冒充 H2-X 或原 TypeScript 字节身份。

通过码：

`PASS-H2N-NUMERICALLY-QUALIFIED-BACKEND-CANDIDATE-ONLY`

即使 H2-N 通过，也不证明物理模型正确。

### 9.4 CPU native 和 GPU 的处置

当前证据不足以直接选 native/GPU，也不足以直接淘汰。

- CPU native/OpenMP：应先尝试严格浮点选项和静态分区；若可实现逐字节相同，可进入 H2-X，否则进入 H2-N。
- GPU：原则上视为 H2-N，除非完整人口、力和 payload 在所有 H2-X 门上逐字节相同。
- CPU/GPU hybrid：必须有结果前负载分割和归约语义；不得根据科学值动态分配。

## 10. H3 精确解锁条件

本裁决不解锁 H3。

H3 只在一次集中 `PR-2B` 审查接受以下全部证据后解锁：

1. HW2R v2 合同、schema、测试、实现和完整矩阵均在性能观察前冻结；
2. 所有配置类别均已重跑或有有效静态 `NO-GO/DEFERRED`；
3. 不存在测量无效且可能快 10% 以上的候选；

5. 选中后端吞吐达到全部合格候选最佳值的至少 95%；
6. CPU 扩展/带宽或 GPU 利用/传输/同步证据闭合；

`UNLOCK-HW1-PRIMARY-AND-HW1-REPEAT-ONLY`

## 11. 全项目技术债总图

### 11.1 P0：HW2 测量语义与科学路径脱节

当前 HW2 合成 u32 路径与 A8R 操作图差异过大。必须重建代表性测量层，而不是微调 15 秒门或只重跑 GPU。

处置：中等规模重构 H1/HW2 候选数据面。

### 11.2 P0：A8R 顶层串行和无 case 级持久化

现有资格入口同步运行八 case，直到全部返回才写最终 gzip。中断前已完成的 case 没有认证 shard。

处置：在新候选执行层建立 case pool、atomic shard、确定性聚合和同运行身份的 case 边界恢复。保持旧科学源不动。

### 11.3 P0：分析步全人口复制和对象化 trace

A8R 在每个分析步复制 pre/post 全人口，复算完整力身份，扫描场诊断，并把多层对象保存在 trace 中。该路径保证审计性，但造成高内存、GC 和带宽压力。

处置：

- H2-X 首先不改变 case 内语义；
- 通过紧凑列式 shard、及时序列化已完成 case 和父进程不持有全部对象降低峰值；
- 若要消除人口复制或融合审计，属于新数值实现，必须 H2-N。

### 11.4 P0：执行身份、科学身份和产物身份仍未贯穿正式程序

H1 已定义三层 provenance，但正式 GUI/CLI 和一般模拟结果仍以较粗的 backend/contract hash 为主。

处置：H3 先在候选路径闭合三层身份；PR-3 后再定点接入正式程序。

### 11.5 P1：G0/H1/E1/F1/S1 重复 canonical 实现和包脚手架

多个候选包分别维护相似的 canonical JSON、SHA-256、clone、package 和测试代码。继续复制会增加治理成本和语义漂移。

处置：

- 既有冻结文件不回改；
- 新建 `90_候选工作区/current/_shared/**`，仅服务后续版本；
- 共享 canonical、sidecar、finite-tree、contract loader、test fixture；
- 每个旧证据继续绑定旧实现哈希；
- 不用“去重”改写历史证据。

### 11.6 P1：合成资格与正式实现之间缺少桥接

F1、S1、E1 的合成 PASS 主要证明候选协议和工具。正式前向、正式结构和正式 CSV/UI 尚未逐项绑定这些合同。

处置：新增正式只读桥接测试；PR-3 后在 I1 做定点集成。

### 11.7 P1：正式 CI 覆盖不足

当前 simulation workflow 只运行 G0/H1/E1/F1/S1。正式 `02_模拟程序` 已有 `npm run validate`，但不在统一 CI 中。

处置：下一阶段增加不含长研究矩阵的正式 CI job：

- `npm ci`;
- `npm run test`;
- `npm run build`;
- `npm run desktop:check`;
- `npm run test:e2e`;
- `npm run docs:check`.

共享 runner 环境不能作为本机性能证据。

### 11.8 P1：正式 GUI 只有单 worker 控制面

正式 `SimulationRunner` 持有一个 Worker，worker runtime 同时只有一个 active run。它解决 UI 响应性，不是硬件 worker pool。

处置：H2/H3 先使用独立候选 runner。只有 PR-3 接受后才考虑把受资格的 scheduler 接入 GUI/CLI。

### 11.9 P1：默认系数仍是示例文献先验

正式默认配置使用 `illustrative-literature-prior-v1` 和 `literature-prior`。项目还不是装置定量预测器。

处置：I1 必须显式区分 illustrative、calibrated、holdout，并接入 E1 的单位、来源、不确定度、装置和校准身份。

### 11.10 P1：活动治理文件多，历史和活动路径混杂

大量不可变合同、裁决和证据是审计资产，但会增加导航成本。

处置：

- 保留历史字节；
- 继续维护机器总账和 supersession；
- 建立活动命令索引；
- 每个工作包只列活动版本；
- Z1 扫描所有 `PENDING/TODO/NOT RUN` 并分类。

### 11.11 P2/P3：物理范围扩张

三维、自由表面、强耦合、非反射边界新路线和装置专属 CFD 仍无实验判别依据。

处置：保持 `DEFERRED-PHY-AWAITING-PR3-OR-EXPERIMENT-TRIGGER`。不因硬件可用而扩大物理范围。

## 16. 风险登记和主机安全

### R-PR2-01：主机关机再次丢失长时结果

缓解：H3 atomic case shard、同运行 case 边界恢复、partial 隔离、primary/repeat 不共享。

### R-PR2-02：16 GB 内存限制

缓解：静态每 worker 上界、专用 cgroup、4 GiB/25% 系统保留、动态 worker 上限、无 swap 增长、逐级扩展。

### R-PR2-03：GPU 与无关进程冲突

缓解：发现外来 GPU 进程时仅 `DEFERRED-UNSAFE-TO-PROBE`；不得停止、迁移、降优先级或 reset。

### R-PR2-04：热降频误判性能

缓解：20–45 秒重复、独立 soak、CPU/GPU 频率与 throttle、前后温度、批次作废而不是选择性保留。

### R-PR2-05：结果后协议漂移

缓解：v2 合同和自动放大规则先提交；正式重复后不得调整工作量或门。

### R-PR2-06：native/GPU 与 TypeScript 语义漂移

缓解：H2-X 全字节门；不通过即 H2-N；新 backend ID；不得自动 fallback。

### R-PR2-07：历史治理成本继续上升

缓解：future-only 共享工具、机器 ledger、活动索引、旧证据不改写、PR 复核点集中。

### R-PR2-08：正式程序过早集成

缓解：PR-3 前 `02_模拟程序/**` 只读；候选和正式身份分离。
